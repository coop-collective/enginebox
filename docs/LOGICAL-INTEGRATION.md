# Logical LayerFS integration

Enginebox owns change submissions, the batch queue, native execution, candidates and acceptance. Gamejam can present this state through its authenticated adapter. It does not merge Stores or coordinate batches.

The supported executor uses the product's pinned LayerFS SDK (`968a5d0be0ea3e9456b06f9148b65523138e9490`) and **one node-local Store**. A submission binds an already published generation to an immutable LayerFS Commit or Layer reference and its filesystem root. Commit/Layer references are 66 lowercase hex characters, including the `12`/`32` tag. An independent Store cannot be attached or merged as a SQLite file. Missing references fail visibly; cross-Store logical import remains unqualified.

## Operator flow

1. Import a reviewed source tree using the existing storage CLI with `--source-only`. This omits Git metadata; legacy Git-bearing imports are refused by this executor. `ebox --host local storage layerfs --config PRIVATE_CONFIG snapshot PROJECT NAME --reference main` freezes main and makes a private online SQLite backup. The response supplies `snapshot`, `ref`, `root`, `projectName` and `layerfsRevision`. Publish that backup with those reference bindings in generation metadata and accept the initial base through the existing owner API.
2. Agents work on isolated LayerFS branches and checkpoint results. Snapshot each immutable result with `snapshot PROJECT NEW_NAME --reference COMMIT_OR_LAYER_ID`. Publish with `parent` equal to the accepted base and metadata `projectName`, `layerfsRevision`, `layerfsRef`, `layerfsRoot`. Main is never overwritten by this operation.
3. The owner submits `POST /v1/projects/PROJECT/submissions`: `{id, task?, project, base, generation, layerfsProject, baseRef, baseRoot, ref, root}`. `id` is an immutable submission identity; optional `task` associates a durable task (defaults to `id`). Reworked tasks use new submission IDs. Repeating an identical submission is idempotent; changing its specification returns 409. The controller captures current task requirements itself.
4. Queue `POST /v1/projects/PROJECT/integrations` with `{id,changes:[SUBMISSION_ID,...]}`. This freezes 1–128 distinct submissions in order, one exact accepted base, task requirements and protected check recipes. Duplicate task membership is refused. The operator CLI is `node packages/fleet-dev/src/integrate.mjs PRIVATE_CONTROLLER_CONFIG submit PROJECT SUBMISSION_JSON` or `queue PROJECT BATCH_ID SUBMISSION_ID...`; config contains `controller` and an owner `token`.
5. An enrolled worker with `integrationProjects:[PROJECT]` receives a normal durable native lease. Its private integration config binds `binary`, `config` and `projects:{fleetProject:layerfsProject}`. Task-only MCP credentials cannot submit, poll, execute, publish or finish integrations. The node invokes `ebox --host local storage layerfs --config PRIVATE_CONFIG integrate --request PRIVATE_REQUEST`.
6. The executor forks immutable refs into private branches, proves that each result descends from the stated base, and invokes native `branch.merge` sequentially into new branches. It never calls `branch.publish`. Native three-way text merging and identical/disjoint changes are supported; overlapping text, binary, delete/type/metadata disagreements fail with upstream conflict detail. Any `.lww` resolution is refused. SQLite is backed up after this logical merge, never merged.
7. The worker publishes the verified backup as a new generation whose parent is the frozen base. Completion stages the frozen candidate after checking output provenance, current requirements, unchanged check policy and accepted base. It does **not** manufacture successful checks or accept the head. Protected builds/tests and owner/policy acceptance remain separate.

## Source export and recovery

Exports live under `CONFIG.root/integrations/FLEET_PROJECT/BATCH_ID/{source,source.json,store.sqlite}`. The sibling `BATCH_ID.json` receipt binds the request and outcome. Private branch/workspace names derive from the project and batch identity. A completed identical request returns its receipt; any incomplete/uncertain request refuses automatic replay. Native reservations retain capacity across uncertain attempts until explicit reconciliation. A rebased batch uses a new identity and freshly published results.

`source.json` contains `{schema:1,project,generation,layerfs:{revision,project,ref,root},treeHash,entries}`. Entries are sorted by UTF-8 path, using canonical sorted-key JSON for `treeHash = SHA256(entries)`. Files record `{path,kind:'file',sha256,size,executable}`; symlinks record `{path,kind:'symlink',target}`. Paths and symlink chains must remain inside the source. Private metadata, credential paths, generated engine caches, special files and excessive inventories are refused. Generation is set to the published output by the node adapter before builds consume it.

The export is archived **inside** the private FUSE mount namespace, then copied as a regular archive and hashed after extraction. Direct `docker cp` of a dynamic FUSE mount can silently return an empty directory and must not be used. The configured image and Linux executor require `tar`. This is a source snapshot, not a running editor or memory snapshot. Cache artifacts, engine binaries, build recipes and playtest recordings are independent artifacts.

The first executor is operator driven and same-Store only. It does not automatically rebase a stale batch, select tests to skip, implement binary asset conflict resolution, upgrade the SDK, or merge changes into production. Existing storage roots bind their exact bridge contents; a bridge update requires explicit migration to a newly provisioned root, never silent adoption of an active Store. LayerFS's current durability and garbage-collection limits in `LAYERFS-VALIDATION.md` still apply.
